## What each column means, and what measured it

- **Reachable**: a hard GET to the URL returns the shell, so a refresh or a bookmark works
- **Renders**: the surface renders without an uncaught fault
- **Heading**: exactly one h1, or the surface is documented as chrome-less
- **Controls**: every button and link has an accessible name
- **States**: loading, empty, error and success states exist
- **Responsive**: not yet - a phone is the Mobile module, not this one; this column waits on a merged mobile matrix
- **a11y**: keyboard reachable, named, reduced-motion respected
- **Notes**: anything about the surface a reader needs to know.

## Known gaps

Recorded rather than hidden, so nobody reads a dash as a pass:

- **States, Responsive and a11y are not yet measured per page.** The harness
  asserts them across the whole run (every control carries an accessible name),
  but not per route. Filling those columns is phase one of the rebuild.
- **This matrix covers the Desktop module, which has no phone arrangement.**
  A phone is served the Mobile module - a second, independent entry with its own
  document, entry module and shell over the same platform. It is rendered and
  checked by `check:mobile-render.js` and `check:mobile-layout.js`, whose per-route
  results are not merged into this table.
- **The public site is redesigned for desktop; its phone composition is not.
  It is on the canonical tokens and its desktop layout is the new one - verified
  by `check-public-site.js` - but it has no purpose-built phone layout of its
  own. A responsive desktop layout is not a mobile design.
